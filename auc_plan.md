# План реализации аукционов на `/auc`

## Цель первой версии

Добавить в текущий проект отдельную страницу `/auc` с двумя режимами аукциона для стрима:

1. **Лидерный аукцион вариантов** — побеждает вариант, на который собрана максимальная сумма.
2. **Взвешенное колесо** — шанс варианта на победу пропорционален общей сумме ставок на него.

Проект не нужно переписывать на новый фреймворк. Публичную часть можно оставить на HTML/CSS/JS, а состояние аукциона и выбор победителя вынести в отдельный Python API с SQLite. Это необходимо, чтобы таймер, ставки и результат не зависели от браузера стримера и сохранялись после перезапуска.

## Границы MVP

В первую версию входят:

- один активный аукцион одновременно;
- режимы `leader` и `weighted-wheel`;
- публичная страница по точному адресу `/auc`;
- интерфейс администратора/модератора;
- просмотр аукциона без авторизации;
- суммы в рублях с хранением в целых копейках;
- название, описание/правила, варианты и длительность аукциона;
- ручное добавление ставок модератором;
- запуск, завершение и отмена аукциона;
- сохранение результата и журнала действий;
- честный серверный выбор победителя для колеса.

Не входят в первую версию:

- прием платежей самим сайтом;
- интеграции с DonationAlerts/DonatePay;
- ставки против варианта;
- досрочный выкуп;
- бесконечный аукцион;
- анти-снайпинг и автоматическое продление таймера;
- повышающие коэффициенты;
- несколько победителей;
- мультивалютность;
- аккаунты зрителей;
- возвраты и escrow.

Интеграции с донат-сервисами нужно добавить следующим этапом через адаптер входящих событий, не смешивая их с основной логикой аукциона.

## Правила режимов

| Параметр | Лидерный аукцион | Взвешенное колесо |
|---|---|---|
| Основное представление | Список/рейтинг вариантов | Колесо и таблица вариантов |
| Победитель | Вариант с максимальной суммой | Случайный вариант с весом `сумма варианта / общая сумма` |
| Равенство | Честная жеребьевка между лидерами | Не требует отдельного правила: каждый вариант уже участвует своим весом |
| Момент определения | После атомарного закрытия приема ставок | На сервере после атомарного закрытия приема ставок |
| Один вариант с положительной суммой | Побеждает автоматически | Побеждает автоматически |
| Общая сумма равна нулю | Победитель не определяется | Победитель не определяется |

Для равенства в лидерном аукционе рекомендуется случайный выбор среди лидеров с раскрытием данных жеребьевки. Это понятнее и честнее, чем преимущество первому или последнему донату.

## Структура файлов

Предлагаемая структура:

```text
auc/
  index.html          # страница зрителя и администратора
  auc.css             # стили страницы
  auc.js              # состояние интерфейса, API и обновления
  wheel.js            # расчет геометрии и SVG-анимация колеса

auction_api.py        # отдельный HTTP API аукциона
test_auction_api.py   # тесты доменной логики и API

deploy/
  nginx-auc.conf
  moralsqd-auction.service
```

Дополнительно:

- добавить ссылку на `/auc` в навигацию главной страницы;
- использовать текущие визуальные токены и стили проекта;
- не расширять сгенерированный `support.js` логикой аукциона;
- подключать ресурсы страницы абсолютными путями, чтобы прямое открытие и обновление `/auc` работали корректно.

## Интерфейс `/auc`

### Публичная часть

- ссылка назад на основной сайт;
- название и описание текущего аукциона;
- понятное название режима;
- статус: черновик, идет, закрывается, завершен или отменен;
- таймер, рассчитанный относительно серверного времени;
- общая собранная сумма;
- список вариантов с суммами и долями;
- рейтинг для лидерного режима;
- SVG-колесо для взвешенного режима;
- последние принятые ставки без чувствительных данных;
- итоговый победитель;
- данные для проверки честности жеребьевки.

### Административная часть

- вход через серверную сессию;
- создание нового аукциона;
- выбор режима;
- добавление, редактирование, объединение и удаление вариантов до запуска;
- ручное добавление ставки;
- исправление ошибочной ставки через отмену записи и создание новой;
- запуск, досрочное закрытие и отмена аукциона;
- принудительное разрешение спорной ситуации с обязательным указанием причины;
- просмотр журнала действий.

Админка может находиться на той же странице `/auc`, но административные методы должны быть защищены подписанной `HttpOnly`-сессией. Секретный URL сам по себе авторизацией не считается.

## Состояния аукциона

```text
DRAFT -> OPEN -> LOCKED -> RESOLVING -> FINISHED
             \-> CANCELLED
```

- `DRAFT` — можно менять настройки и варианты, ставки не принимаются.
- `OPEN` — ставки принимаются, таймер идет.
- `LOCKED` — прием ставок уже закрыт, зафиксирован финальный снимок данных.
- `RESOLVING` — сервер определяет и сохраняет победителя.
- `FINISHED` — результат неизменяем и доступен зрителям.
- `CANCELLED` — аукцион отменен с указанием причины.

После перехода в `LOCKED` нельзя принимать новые ставки или снова открыть тот же аукцион. Для продолжения создается новый аукцион.

## Backend и хранение данных

Запустить отдельный сервис аукциона:

- адрес приложения: `127.0.0.1:8788`;
- публичный префикс API: `/api/auc/`;
- база: `/var/lib/moralsqd-auction/auction.db`;
- секреты и настройки: `/etc/moralsqd-auction.env`;
- наружу API отдается через существующий nginx.

Основные таблицы:

- `auctions` — настройки, режим и состояние аукциона;
- `options` — варианты и их порядок;
- `contributions` — принятые ставки;
- `snapshots` — финальное состояние сумм в момент закрытия;
- `results` — победитель и данные жеребьевки;
- `audit_events` — административные действия и причины изменений.

Ставки должны быть неизменяемыми. Ошибка исправляется созданием отменяющей записи и новой корректной записи. Для будущих интеграций нужна уникальность по `(provider, external_id)`, чтобы повторно доставленный webhook не удвоил сумму.

Для MVP достаточно обновлять публичное состояние polling-запросом раз в 1–2 секунды. WebSocket на первом этапе добавит сложности, но почти не даст пользовательской пользы.

## Минимальный API

Публичные методы:

- `GET /api/auc/current` — текущий аукцион, варианты, суммы, статус и серверное время;
- `GET /api/auc/{id}/result` — сохраненный результат и данные проверки;
- `GET /api/auc/{id}/contributions` — безопасный публичный список последних ставок.

Административные методы:

- `POST /api/auc/admin/login`;
- `POST /api/auc/admin/auctions`;
- `PATCH /api/auc/admin/auctions/{id}`;
- `POST /api/auc/admin/auctions/{id}/options`;
- `POST /api/auc/admin/auctions/{id}/contributions`;
- `POST /api/auc/admin/contributions/{id}/void`;
- `POST /api/auc/admin/auctions/{id}/start`;
- `POST /api/auc/admin/auctions/{id}/close`;
- `POST /api/auc/admin/auctions/{id}/cancel`.

Все изменяющие административные запросы должны проверять сессию, CSRF-токен, входные данные и допустимость перехода состояния.

## Честность взвешенного колеса

Браузер не должен самостоятельно выбирать победителя. Он только анимирует уже сохраненный сервером результат.

Схема выбора:

1. При запуске сервер генерирует секретный `seed` и публикует его хеш-коммитмент.
2. При завершении сервер в одной транзакции закрывает прием ставок и создает канонический снимок вариантов и сумм.
3. Снимок сериализуется в стабильном порядке и хешируется.
4. Из `seed` и хеша снимка через HMAC получается целое случайное число.
5. Число попадает в один из диапазонов, длины которых равны суммам вариантов.
6. Победитель и все исходные данные сохраняются до запуска анимации.
7. После завершения раскрываются `seed`, снимок и алгоритм проверки.

Пример:

```text
Фильм A: 3000 ₽ -> 60%
Фильм B: 1500 ₽ -> 30%
Фильм C:  500 ₽ -> 10%
```

Колесо должно визуально соответствовать этим долям. Маленькие сектора нельзя искусственно увеличивать, иначе картинка будет обещать шанс, которого на самом деле нет.

## Безопасность

- серверная проверка всех сумм, идентификаторов и переходов состояния;
- хранение денег только целыми числами в копейках;
- параметризованные SQL-запросы;
- экранирование пользовательских названий и комментариев;
- запрет HTML в названиях вариантов;
- `HttpOnly`, `Secure`, `SameSite` cookie для админ-сессии;
- CSRF-защита для изменяющих запросов;
- rate limit для входа и административных операций;
- неизменяемый audit log;
- атомарное закрытие аукциона и расчет результата в транзакции;
- запрет повторной обработки внешнего события;
- отсутствие персональных и платежных данных в публичном API.

## Этапы реализации

### 1. Маршрут и каркас страницы

- создать `auc/index.html`, стили и JS;
- настроить точный маршрут `/auc` и корректный refresh;
- добавить ссылку с главной страницы;
- сделать адаптивный каркас публичной и административной частей.

### 2. Серверное ядро

- создать схему SQLite и миграцию начальной версии;
- реализовать модель состояний;
- добавить публичное чтение состояния;
- добавить админ-аутентификацию, CSRF и базовый rate limit;
- обеспечить транзакции и audit log.

### 3. Лидерный аукцион

- создание вариантов;
- ручные ставки;
- расчет сумм и рейтинга;
- серверный таймер и атомарное закрытие;
- определение победителя и жеребьевка при равенстве;
- сохранение и отображение результата.

После этого этапа уже должен существовать полностью рабочий вертикальный сценарий.

### 4. Взвешенное колесо

- расчет весов только на сервере;
- SVG-отрисовка секторов;
- commit/reveal и воспроизводимый выбор победителя;
- анимация до сохраненного результата;
- запасной режим без анимации при `prefers-reduced-motion`;
- отображение формулы и данных проверки.

### 5. Интеграция реальных донатов

- выбрать первый сервис: DonationAlerts или DonatePay;
- проверить подлинность webhook;
- дедуплицировать внешние события;
- автоматически сопоставлять точное название варианта;
- неоднозначные сообщения отправлять в очередь модератора;
- хранить сырой payload отдельно от публичных данных.

Этот этап стоит начинать после готовности ручного сценария: тогда интеграция будет только новым источником ставок, а не частью доменной логики.

### 6. Тестирование и деплой

- unit-тесты расчетов, ничьей, weighted draw и переходов состояния;
- API-тесты авторизации, идемпотентности и гонки при закрытии;
- проверка XSS и некорректных сумм;
- мобильная проверка и проверка Browser Source в OBS;
- проверка режима уменьшенного движения;
- обновление скрипта деплоя для рекурсивной публикации папки `auc`;
- установка systemd-сервиса;
- `nginx -t` перед reload;
- внешняя проверка `/auc` и `/api/auc/current` после публикации.

## Критерии готовности MVP

- `/auc` открывается напрямую и после обновления страницы;
- неавторизованный пользователь не может менять аукцион;
- администратор полностью проводит оба режима от черновика до результата;
- для сумм 3000/1500/500 колесо показывает и использует вероятности 60/30/10;
- ставки, пришедшие после момента закрытия, не попадают в результат;
- повтор одного внешнего события не меняет сумму дважды;
- перезапуск сервиса не теряет активный аукцион и результат;
- результат колеса сохраняется до анимации и воспроизводимо проверяется;
- пользовательские строки не позволяют выполнить HTML/JS;
- страница корректно работает на мобильном экране и в OBS Browser Source;
- существующая главная страница и текущие тесты проекта продолжают работать.

## Решение, которое нужно принять перед интеграцией

Для ручного MVP дополнительных продуктовых решений не требуется. Перед этапом реальных донатов нужно выбрать первого провайдера — DonationAlerts или DonatePay — и зафиксировать формат команды, по которой сообщение доната сопоставляется с вариантом.
